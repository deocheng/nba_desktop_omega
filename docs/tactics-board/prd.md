## 1. 产品目标

**一句话目标**：为 NBACore Studio v8 提供「半场战术板 + 战术模板演示 + PBP 动态回放」能力，让用户以「双色带号圆圈移动 + 篮球移动 + 事件标注」的极简可视化方式，理解和复盘常见 NBA 战术与真实比赛事件。

**成功标准（可度量）**：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 战术板摆位 | 支持双方各 ≤5 名球员（双色、带号码或姓名缩写），拖拽摆位响应 < 100ms | 纯前端 SVG 交互 |
| 战术模板库 | 内置 ≥8 个常见战术模板，一键加载 ≤ 1s | 见 §7 初始清单 |
| 动画流畅度 | 前端渲染帧率 ≥ 30fps（rAF 推进） | 帧数据由后端 Engine 生成 |
| PBP 回放覆盖 | 覆盖 2020–2026 全部有 xy 的赛季（仅这些赛季有坐标回填） | 数据摸底已确认 |
| 架构合规 | 100% 坐标映射/插值/动画序列生成发生在后端 Engine 层 | 验收依据 §4 架构约束 |
| 简洁动画 | 仅使用「圆圈移动 + 篮球移动 + 事件气泡标注」，无粒子/3D/过渡炫光特效 | 用户硬性要求 |

## 2. 用户故事（覆盖 6 项能力）

- **US1（战术板摆位）**：As a **教练/分析师**, I want **在半场底图上拖拽放置双方球员（两种颜色圆圈，带号码或名字）** so that **我能自由摆出任意进攻/防守站位进行讲解**。
- **US2（战术模板库）**：As a **篮球爱好者/解说**, I want **一键加载常见战术模板（如挡拆、Horns、Floppy 等），自动出现初始站位与移动路线箭头** so that **我不用从零画起就能快速理解战术跑位**。
- **US3（战术动态演示）**：As a **学习者**, I want **按模板的路线/时序播放动画，球员圆圈沿路径移动、篮球随战术移动** so that **我能直观看懂战术的跑位与传球逻辑**。
- **US4（PBP 动态回放）**：As a **数据分析师**, I want **选择一场比赛，按 play_by_play 事件序列动态回放——球员移动、投篮动作、命中/投失/助攻/篮板/犯规均有动态标注** so that **我能复盘真实比赛的关键回合而不只是看文字记录**。
- **US5（简洁动画原则）**：As a **所有用户**, I want **只用双色带号圆圈 + 篮球移动 + 事件标注（✅/❌/AST/REB/PF）** so that **信息清晰聚焦、加载快、在低配设备也能流畅播放**。
- **US6（AI 战术生成 · 规划）**：As a **高级用户**, I want **未来能用自然语言描述战术、由 AI 生成可加载的战术模板，或从真实 PBP 提炼战术** so that **战术库能持续扩展、与个人打法偏好对齐**（v1 仅预留接口，不实现）。

> 优先级定义：**P0** 必须有（v1 核心）、**P1** 应该有（v1 增强）、**P2** 规划项（v1 不实现，但预留可插拔接口与数据结构）。

### 3.3 P2 — 规划项（v1 不实现，预留可插拔接口）

> ⚠️ P2 为**规划/路线图能力**：v1 不交付功能，但必须预留接口契约与数据结构，使后续迭代（含 Mac+Ollama 接入）可无重构接入。详见 §6。

| 优先级 | 编号 | 需求 | 做什么（规划） | 验收口径（接口级） |
|--------|------|------|----------------|--------------------|
| P2 | TB-14 | AI 战术生成接口（自然语言→模板） | 定义 `TacticGenerator` 可插拔接口：`generate_from_natural_language(prompt, constraints) -> TacticTemplate`；v1 提供 `CuratedStubProvider` 占位实现 | 接口契约存在且可 import；Stub 返回内置模板；单测覆盖接口签名 |
| P2 | TB-15 | 从真实 PBP 提炼战术 | 扩展接口：`extract_from_pbp(game_id, segment) -> TacticTemplate`；由 LLM 从事件序列归纳跑位模式 | 接口契约存在；预留输入/输出 schema |
| P2 | TB-16 | Mac + Ollama 接入（远期） | 实现 `OllamaProvider`（本地 LLM，离线/隐私），与项目「Mac 版接入 Ollama」远期目标对齐；可选 `RemoteLLMProvider` | 接口与 OllamaProvider 插槽预留；不要求 v1 运行 |

## 4. 非功能需求与架构约束

### 4.1 四层严格隔离（v8 合同第 2 章 / 第 6 章）

```
flowchart LR
  F[Frontend 层<br/>SVG 渲染 + rAF 推进帧] -->|调用 API| API[API 层<br/>纯编排, 禁 SQL/计算]
  API -->|调用 Engine| ENG[Engine 层<br/>坐标映射+插值+动画序列生成]
  ENG -->|批量 SELECT| DB[(Data 层<br/>play_by_play 只读)]
```

- **Frontend（Layer 4）**：仅负责调用 API + 按 Engine 返回的「逐帧坐标序列」渲染 SVG；动画播放（requestAnimationFrame 推进帧）可在前端，但**帧数据必须由后端生成**；**禁止任何坐标映射/插值/聚合/过滤计算**。
- **API（Layer 3）**：仅编排——接收请求、调用 Engine、返回结构化帧序列；**禁止 SQL、禁止计算、禁止业务逻辑**。
- **Engine（Layer 2，唯一计算点）**：`backend/services/tactics_engine/` 负责坐标映射（x/y→SVG 像素）、事件间插值、占位策略、动画帧序列生成；所有计算必须在此完成，输出 deterministic。
- **Data（Layer 1）**：仅 `play_by_play` 只读访问；必须带 season/date 过滤的 **batch 查询**；**禁止 per-player/per-row 循环查询**；所有 SQL 可 trace。

### 4.2 坐标系统一映射（待架构师确认）

- 源数据：`play_by_play` 的 `x`(integer)、`y`(integer)、`dist`(integer)。坐标覆盖率：全表 1817 万行中 **1531 万行有 x/y**（来自 `source='br_crawler'` 回填批次）。
- 坐标语义：投篮事件有真实 x/y（如 (176,94)、(-231,7)）；非投篮事件（换人/篮板/犯规等）x/y 为 (0,0) 占位。
- 量级（观测）：约 x∈[-250,250]、y∈[0,94]（半场，篮筐端在 y 小值侧）。**具体 x/y → 半场 SVG 像素的映射公式与朝向，列为待架构师确认项（§8 ④）**，PRD 不预置。
- 插值策略：投篮位置可真实还原；球员连续移动路线数据缺失，需用「事件间线性插值 + 占位策略（非投篮事件用上一已知位置 或 球场语义位置）」呈现（见 §8 ⑦）。

### 4.3 写路径约束（若启用模板持久化）

- 若 P1-TB-11 启用用户自建模板保存，写库须使用**专用连接池** + **参数化 SQL（预编译语句）**，符合 v8 §6 禁则（no dynamic SQL、no eval/exec）。

### 4.4 性能与确定性

- 动画序列生成 deterministic（相同输入→相同帧序列）；前端渲染 ≥30fps；模板加载 ≤1s；单场比赛 PBP 回放首帧 ≤2s（取决于数据抽取）。

### 4.5 兼容性

- 半场即可，不必要全場；桌面端（Chrome/Edge/Safari 最新版）为首要目标；移动端自适应为 P2 可选。

## 6. AI 路线图专章

### 6.1 能力定义

- **自然语言生成战术**：用户输入一句自然语言（如"右侧高位挡拆后分球底角三分"），系统产出可加载的 `TacticTemplate`（初始站位 + 移动路径 + 篮球路径）。
- **从真实 PBP 提炼战术**：给定一场比赛的一个回合/片段，由模型从 play_by_play 事件序列归纳出跑位模式并抽象为模板。

### 6.2 触发方式（规划）

- 战术板页面提供「**AI 生成**」入口按钮（v1 灰显、标注"即将上线"）。
- 触发后：调用 `TacticGenerator.generate_from_natural_language(prompt, constraints)` → 返回 `TacticTemplate` → 载入战术板演示。
- 提炼模式：在 PBP 回放界面选择片段 → `TacticGenerator.extract_from_pbp(game_id, segment)` → 生成模板。

### 6.3 可插拔接口预留（与 Ollama/LLM 对齐）

```text
# 抽象接口（v1 必须落地契约，不要求真实 LLM）
TacticGenerator (协议/抽象基类):
  generate_from_natural_language(prompt: str, constraints: dict) -> TacticTemplate
  extract_from_pbp(game_id: str, segment: dict) -> TacticTemplate

# 实现后端（P2 迭代）
- CuratedStubProvider   : v1 占位，返回内置模板，保证接口可测、可运行
- OllamaProvider        : 本地 LLM（Mac 版默认，离线/隐私优先）—— 远期目标插槽
- RemoteLLMProvider     : 可选云端 LLM API 插槽
```

- v1 必须：定义 `TacticTemplate` 数据结构与 `TacticGenerator` 接口签名，并提供 `CuratedStubProvider`，使后续 Provider 可「插拔」接入而**无需改动 Frontend/API/Engine 调用链**。
- 数据结构预留：模板含 `formation`（5 人初始站位，球场相对坐标）、`steps`（动作序列）、`ball_path`，与 P0 战术模板库共用同一 schema（§7 参考）。

### 6.4 为何放入 P2（v1 不实现）

1. **前置依赖**：v1 必须先夯实坐标映射、插值、动画序列生成等确定性基础（P0），AI 生成才有可信的输入/输出载体。
2. **基础设施缺口**：LLM/Ollama 运行环境与 Mac 版平台目标尚未就绪，不在 v1 交付范围。
3. **风险隔离**：AI 生成属非 deterministic 能力，与 v8 合同「所有输出 deterministic、可验证」原则存在张力，宜作为独立规划项单独评审。

### 6.5 与 Mac 版 Ollama 远期目标的关系

- 项目远期目标包含「Mac 版接入 Ollama」实现本地离线 LLM。**`OllamaProvider` 插槽即为该目标在战术板模块的前向接口**；v1 仅预留，待 Mac 版与 Ollama 运行时到位后，可在不重构的前提下接入，实现离线、隐私友好的战术生成。

### 7.1 战术板/动画常见数据建模参考（用于模板数据结构）

- **声明式指令模型（参考 Schematex DSL）**：用最少指令表达战术——`players {1..5}` + `commands[screen, cut, pass, dribble]` + 语义位置标签（top/lwing/rwing/elbow/corner…）或球场坐标。优点：教练可读、易扩展（meta 含 complexity/version）。来源：schematex.js.org/examples/playbook-basketball-floppy。
- **位置点序列 + SVG 路径 + 时序**：每个球员建模为有序 `(t, x, y)` 点序列；篮球单独路径；事件在时间戳上标注。战术模板可存「初始 formation + 有序 steps（action, actor, path polyline）」，由 Engine 展开为逐帧坐标。参考：DiagramTheGame / CourtBook 等战术板工具的「drag players → draw paths → animate」范式。
- **PBP 回放建模**：按事件序列读取 play_by_play 行 → 映射 x/y→像素 → 对 (0,0) 占位事件做插值/语义占位 → 输出帧列表 `{t, players:[{id,color,label,x,y}], ball:{x,y}, annotations:[{type,text}]}`。

> 结论（供架构师）：v1 战术模板与 AI 生成的 `TacticTemplate` 共用同一数据结构（formation + steps + ball_path），前端只消费 Engine 生成的逐帧序列，不感知上述建模细节。
