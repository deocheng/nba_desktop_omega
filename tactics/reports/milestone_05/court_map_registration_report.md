## 1. 问题定义

### 1.1 表层:原 courtmap 只有 2 条图元

`engine/run_ball_events.py::_courtmap()` 原实现仅绘制:

```python
cv2.line(cv, (0, H//2), (W, H//2), ...)          # 一条横贯中点的线
cv2.circle(cv, (W//2, H//2), 80, ...)            # 半径 80 的小圆
```

即:仅「疑似半场中线 + 疑似中圈」。**边线、底线、三分线全部缺失**,文件名却叫 `courtmap`。

### 1.2 深层:坐标空间错位(关键)

实测 `sas_hou_scores.json` 的球 bbox 分布:

```
X ∈ [84, 1858]   Y ∈ [-2, 1007]      (帧 1920×1080)
```

⇒ 球坐标在**帧像素空间**。转播片段尤其明显:镜头摇到哪球就在哪,**球根本不落在任何「球场图」上**。
若直接把标准球场垫在下面,球轨迹与球场线**毫无几何对应关系** —— 这正是项目「假完整 / 看似有意义实则无」铁律所禁止的。

**⇒ 修复不能只是「多画几条线」,必须先建立帧↔球场的真实映射,否则只是把误导做得更精致。**

## 2. 技术方案:真·球场坐标映射链路

链路三层现成可复用,无需自推数学:

| 层 | 组件 | 职责 |
|---|---|---|
| ① 规范球场几何 | `engine/court_model.py::build_model()` | NBA 94×50ft 米制全量线点集(20 段地板线) |
| ② 帧→球场位姿 | `engine/court_fit.py`(LookCam) | 用规范模型拟合反解相机 `(C, T, f, roll)` |
| ③ 像素→球场逆映射 | `LookCam.to_court(uv)` | **直接把图像像素逆映射到球场地面 (x,y)** |

坐标约定(`court_model` 文件头,全项目统一):

- 世界坐标:米;原点 = 球场中心地板;`+x` 沿长轴(指向右篮),`+y` 沿短轴,`+z` 竖直向上;地板 `z=0`
- 关键常量:`HALF_L=14.3256`、`HALF_W=7.62`、`R_CENTER=1.8288`、`R_3PT=7.239`、`X_LANE=8.5344`、`Y_3PT_CORNER=6.7056`

`court_fit` 自带 `line_map()`(TOPHAT 白度检线)与 `floor_roi()`,**不需要外部线检测模块**。

### 2.1 两类素材的处理策略

| 类型 | 相机特征 | 策略 | 成本 |
|---|---|---|---|
| 宽景四窗 w1–w4 | 固定机位 | 每窗配准 **1 帧**,整窗复用单位姿 | 低 |
| 转播 sas_hou/nop/det | 镜头会动、含特写 | 只配准**球轨迹涉及的唯一帧**(约 80 帧),warm-start 逐帧精修 | 中 |

> 设计要点:不逐帧跑全部 400 帧 —— 既能算出岔值,又能避免逐帧跑 RANSAC 式巨量开销;
> 特写帧无球场线 ⇒ 配准必然失败 ⇒ **诚实跳过**,不画假球场。

### 2.2 新增/修改文件

| 文件 | 状态 | 说明 |
|---|---|---|
| `engine/court_render.py` | 新增 | 真球场渲染 + 配准封装 + `to_court` 映射 + 端到端 CLI |
| `engine/_diag_court.py` | 新增 | 多帧配准诊断(挑最佳代表帧) |
| `engine/court_fit.py` | 修改 | **修 bug**:`score()` 早返回返回元组 |
| `engine/run_ball_events.py` | 修改 | `_courtmap`→`_framespace`(诚实化)+ `--court` 开关 |

### 2.3 验收判据(配准门禁)

单个位姿必须同时满足才算配准成功(否则 `to_court` 映射出的坐标不可信):

```
n_vis   ≥ 150     # 模板线点在帧内可见数
n_trust ≥ 120     # 落在可信区(ROI 内、非贴图遮挡)数
fit = F + R < 9.0 # 正向 + 反向双向平均距离(px),CAP=30
```

- **正向 F**:模型线是否落在实测线像素上
- **反向 R**:实测线像素是否被模型线解释(防止「把球场缩成一团蹭线」)

## 3. 实施过程

### 3.1 修 `court_fit.score()` 真 bug(阻塞级)

现象:`refine()` 走 scipy Powell 时抛 `ValueError: The user-provided objective function must return a scalar value.`

根因:`score()` 在两处早返回**不尊重 `ret_detail`**,恒返回元组:

```python
if vis.sum() < 150:
    return (1e6, ret_detail and {...})     # ← ret_detail=False 时返回 (1e6, False)
```

而网格粗搜的过滤阈值为 `vis≥40 / trust≥30`(比 `score()` 的 150/120 松)⇒ 边界候选必然触发早返回 ⇒ 崩溃。

修复:早返回改为**标量**;仅在显式请求 `ret_detail=True` 时才返回详细字典。

```python
return (1e6, {"why": ..., "n_vis": ...}) if ret_detail else 1e6
```

### 3.2 性能瓶颈定位与优化(实测)

| 阶段 | 观测 | 说明 |
|---|---|---|
| `grid_search` | 3600 位姿 → 2539 有效,**<1s** | 用预计算 DT 查表,很快 |
| `refine` | 25xx 有效 → top **24** 全部精修 | 🔴 **瓶颈**:每次 `obj()` 调用都做一次全图 `distanceTransform` + 折线绘制;Powell 7 维 × 3 轮 **⇒ 数千次 score 调用** |

后果:单帧配准 **10–40 min**,导致一次 8 帧诊断跑至 29 min 仍无输出(另注:后台任务经 `| tail` 管道会把输出缓冲到进程结束,看不到中间进展)。

优化两项:

1. `top`: 24 → **4**
2. 精修前**预筛**:先用 `score()` 排掉返回 `1e6` 的死候选,再只精修活的前 4 个

⇒ 单帧配准降至 **~1–3 min**。

## 4. 验证结果(核心证据)

### 4.1 配准失败:系统性、与选帧无关

诊断对象 `baseline_w1`,覆盖全窗采样帧:

| 帧 | fit (F+R) | n_vis | 判定(<9 为通过) |
|---|---|---|---|
| f00050 | 27.24 | 742 | ❌ FAIL |
| f00150 | 28.20 | 915 | ❌ FAIL |
| **f00250** | **27.92** | 1421 | ❌ FAIL |
| f00350 | 27.10 | 1540 | ❌ FAIL |

```
>> baseline_w1: 全部帧配准失败
```

**四帧互不依赖却同为 fit≈27–28 ⇒ 非选帧问题,是系统性的。**

### 4.2 根因拆解:瓶颈恒在反向项 R

两帧完整分项:

| 帧 | F(正向) | **R(反向)** | n_vis | n_trust | score |
|---|---|---|---|---|---|
| f00100 | 8.29 | **19.38** | 996 | 499 | 27.67 |
| f00250 | 9.00 | **18.93** | 1421 | 680 | 27.92 |

判读:

- **F ≈ 8–9(尚可)** ⇒ 模型线大致落在实测线像素上,**位姿方向基本找对了**
- **R ≈ 19(很差)** ⇒ 大量实测白线像素**模型解释不了**

⇒ 推断:进入线像素图的不仅是球场线,还有转播贴图 / 看台 / 队员防撞高并发白干扰;
`court_fit` 的双向目标函数中反向项被这些不可解释像素长期拉高,无法收敛到可用阈值。

这与该项目里程碑中「球场路线暂停」的判断一致 —— **是同一堵墙,不是新引入的回归**。

### 4.3 已排除的可能性(定向排查)

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 是某帧选得不好 | 4 帧独立配准 | ❌ 排除:全失败且数值一致 |
| 有历史 `courtfit` 产物可复用 | `find -iname "*courtfit*"`(含 backups) | ❌ 排除:无任何产物,必须现算 |
| `n_vis` 不够导致评分无效 | 分项 `n_vis=1421 / n_trust=680` | ❌ 排除:数量充足,分项生效真实 |

## 8. 轻量 B 诊断复盘(按优先级策略执行)

> 策略(用户指定):先做一轮轻量 B 诊断(线像素来源统计 + ROI 收紧),看 R 能否降到个位数;
> **能降就继续打,降不动就果断回 A**,把精力放回球事件/轨迹本身。

### 8.1 诊断方法

`engine/_diag_linesource.py`,三步:

1. **拆 R**:原 `court_fit` 的 R 是 cap 到 30px 后的均值,看不出构成。对每个线像素算它到模型线的距离,
   统计分布与近距离占比(近=被球场模型解释=真球场线;远=不可解释=干扰)。
2. **空间定位**:6×8 网格报「线像素密度 / 远端(>20px)占比」热区,定位干扰所在。
3. **ROI 收紧**:用当前位姿的 `H_ground` 把规范球场四角投影回图像,取多边形为球场 footprint,
   与 `floor_roi` 求交。这是**物理先验**(球场线只可能存在于球场范围内),非「删掉解释不了的点」,
   故不构成自证达标。

### 8.2 结果:根因确证,但迭代不收敛

**默认 ROI(w1 f00250)**

| 指标 | 值 |
|---|---|
| 线像素数 | 24,678 |
| 距离中位 / 未截断均值 | 28.2px / 81.3px |
| ≤5px / ≤10px / ≤20px | 24.7% / 31.6% / 44.8% |
| **>20px(不可解释)** | **55.2%** |

⇒ **超过一半线像素根本不在球场范围内**(看台/转播贴图/场外)。这是 R 高企的确证根因。

**footprint 收紧迭代**

| 轮 | 保留 ROI | **R** | F | fit | 位姿位移 |
|---|---|---|---|---|---|
| 默认 | 100% | 18.93 | 9.00 | 27.92 | — |
| 1 | 25.8% | 11.56 | 7.73 | 19.29 | 11.10 |
| 2 | 24.6% | **10.56**(最低) | 7.72 | 18.28 | 8.55 |
| 3 | 21.6% | **12.13(反弹)** | 7.79 | 19.92 | 8.89 |

收紧一轮的收益是真实的:

- 线像素 24,678 → 11,823(**砍半**)
- 距离中位 28.2px → **6.4px**
- 可解释占比(≤20px) 44.8% → **71.0%**
- R 18.93 → 11.56(**近似腰斩**)

**但迭代不收敛**:位姿每轮仍漂移 8–11,未见稳定;R 在 11.56 → 10.56 → **12.13 回升**。
场内残余 ~29% 不可解释像素(推测为地面赞助图形 / 队员 / 道具)。

### 8.3 判定:回 A(按既定规则)

| 判据 | 结论 |
|---|---|
| R 是否降到个位数 | ❌ 否(最低 10.56,且第 3 轮反弹至 12.13) |
| 位姿是否收敛 | ❌ 否(每轮漂移 8–11) |
| 继续收紧是否正当 | ❌ 再删除「解释不了的像素」= **自证达标**,属无效证据 |

⇒ **果断回 A**,不再消耗算力于配准。已交付的诚实产物维持不变:
`<clip>_framespace_tracks.jpg`(帧空间,显式标注未对齐)+ `court_reference.jpg`(规范球场参考图)。

### 8.4 沉淀教训

1. **被 cap 的均值会掩盖根因**:把 R 拆成每像素距离分布后,「>55% 线像素不在球场范围内」立刻显现;
   只看标量 18.9 无从下手。
2. **物理先验收紧 ≠ 数据 cherry-picking**:按球场 footprint 收缩区域是正当的;
   但按「模型解释不了」删点则是自证达标,必须区分。
3. **多轮迭代必须看「是否收敛」**(见 §8.2 迭代表):单看某轮 R 下降(11.56→10.56)容易误判为「有希望」;
   把**位姿位移与多轮走势**一起看,才发现根本没稳定(R 第 3 轮还反弹)。
